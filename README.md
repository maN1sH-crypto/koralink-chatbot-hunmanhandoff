# KoraLink Customer Support Chat

Flask chatbot and live human support system for the KoraLink website. The project includes an embeddable customer chat page, an agent calling-center dashboard, an English knowledge base, automatic language handling, MongoDB persistence, and temporary image attachments.

## What is in this project

| File or folder | Purpose |
| --- | --- |
| `app.py` | Flask routes, customer and agent APIs, Socket.IO events, session handling, and temporary chat attachments. |
| `scap.py` | Knowledge retrieval and answer formatting, including FAQ images and step images. |
| `bot_work.py` | Sentence Transformer embeddings. Uses `sentence-transformers/all-MiniLM-L6-v2` locally by default. |
| `groq_client.py` | Language detection, translation for knowledge search, answer language handling, and configured LLM fallbacks. |
| `database.py` | Import or replace the MongoDB knowledge collection from `koralink_new.json`, with a recoverable export before replacement. |
| `create_agent.py` | Create or update support-agent and admin logins. |
| `index.html` | Customer chat interface. |
| `static/widget.js` | Embeddable launcher that opens the existing customer chat in a responsive iframe. |
| `templates/agent_dashboard.html`, `static/agent.js`, `static/agent.css` | Calling-center dashboard and its browser behavior/styles. |
| `templates/knowledge_manager.html` | Admin-only English knowledge editor. Changes save to MongoDB. |
| `koralink_new.json` | Current English source knowledge file for initial import/replacement. |
| `data/question_embeddings.npy` and `.hash` | Local embedding cache. It can be regenerated if missing; keeping it avoids needless recomputation. |
| `data/backups/` | Historical MongoDB exports and the pre-translation JSON backup. Keep these until they are deliberately archived elsewhere. |
| `.vscode/settings.json` | Local Live Server port setting for frontend development. |
| `.env` | Private deployment secrets and configuration. Never commit or share this file. |
| `venv/`, `__pycache__/` | Local Python environment and generated bytecode. These are machine-specific and ignored by Git. |

`pdf_source.py` was removed because the current knowledge workflow does not use it. `customer_socket_example.js` is an optional integration example; the real customer UI is `index.html`.

## Chat workflow

1. A customer opens the Netlify-hosted chat. The browser calls the Flask API using the configured backend URL.
2. The backend creates or restores a customer session and saves messages and conversation state in MongoDB.
3. For a bot question, the language layer identifies the input language, prepares an English query, and searches the English knowledge base. The answer is returned in the customer's language where supported; knowledge image URLs and image data remain attached to the response.
4. When the customer requests a person, the conversation enters `waiting_human`. The agent dashboard shows the waiting request.
5. An agent claims the conversation. MongoDB atomically prevents two agents from claiming the same waiting chat. Customer and agent messages are exchanged live through Socket.IO, with polling as a fallback.
6. Customers and agents can send supported image attachments during an active support conversation. Attachments are stored in MongoDB GridFS and automatically purged when the conversation closes.
7. An admin can search, create, edit, deactivate, or delete English knowledge entries in the Knowledge base page. Saves update MongoDB and refresh the running chatbot; normal edits do not require a JSON re-upload or server restart.

Conversation states are `bot_active`, `waiting_human`, `human_active`, and `closed`. Do not run the local development server as the public production service.

## Client setup (Windows, from a clean project copy)

Follow these steps on the computer or server that will run the Flask backend. The chatbot page, agent dashboard, and knowledge manager are served by the same Flask application; the customer page can also be deployed separately to Netlify.

### 1. Install prerequisites

- Install Python 3.10 or newer. During Windows installation, enable **Add Python to PATH**.
- Create a MongoDB Atlas cluster (or prepare a reachable MongoDB server). Create a database user and allow this computer's IP address in Atlas Network Access. For production, allow only the backend host's required IPs; do not leave unrestricted network access enabled.
- Create API keys for Groq, Gemini, and OpenRouter. The current `groq_client.py` initializes all three clients when Flask starts, so configure all three keys even though requests can fall back between providers. Each provider has separate limits and charges.
- Ensure internet access on first launch so Sentence Transformers can download its model. The first launch may take longer than later starts.

### 2. Open the project and create its Python environment

Open PowerShell in the folder containing `app.py`, then run:

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

If PowerShell refuses to activate the environment, open Command Prompt in the same folder and use `venv\Scripts\activate.bat` instead.

### 3. Configure private settings

Copy `.env.example` to a new file named `.env` in the project root. In PowerShell:

```powershell
Copy-Item .env.example .env
notepad .env
```

Fill in the values. Do not paste secrets into this README, source files, screenshots, or Netlify's public source code.

```dotenv
MONGO_URI=mongodb+srv://DB_USER:DB_PASSWORD@YOUR_CLUSTER.mongodb.net/?retryWrites=true&w=majority
DATABASE_NAME=koralink
COLLECTION_NAME=knowledge
SECRET_KEY=replace-with-a-long-random-secret
FRONTEND_ORIGIN=http://127.0.0.1:5000,http://localhost:5000,http://127.0.0.1:5501,http://localhost:5501
EMBEDDING_PROVIDER=local
EMBEDDING_DEVICE=cpu
GROQ_API_KEY=your-groq-key
GEMINI_API_KEY=your-gemini-key
OPENROUTER_API_KEY=your-openrouter-key
PORT=5000
```

Replace the MongoDB username, password, and cluster host with the Atlas values. URL-encode special characters in the database password. Set a long, unique `SECRET_KEY`. Keep `.env` on the backend only; it is ignored by Git and must never be uploaded to Netlify or sent to a client. If the frontend uses a different local port, add that exact origin to `FRONTEND_ORIGIN` as a comma-separated value.

### 4. Import the knowledge base

Check that `koralink_new.json` is present and `.env` points to the intended MongoDB database. For a first setup, run:

```powershell
python database.py
```

This imports or updates knowledge records and creates the indexes. It does not clear the collection. The separate `python database.py --replace-knowledge` option replaces the entire knowledge collection after creating a backup; only use it when a full replacement is intended and the target database has been checked.

### 5. Create the first admin and agent accounts

Create an admin account for managing knowledge:

```powershell
python create_agent.py "Knowledge Admin" admin@example.com "REPLACE_WITH_A_UNIQUE_STRONG_PASSWORD" admin
```

Create one or more agent accounts in the same way, using role `agent` (or omit the final role, since `agent` is the default):

```powershell
python create_agent.py "Support Agent" agent@example.com "REPLACE_WITH_A_DIFFERENT_STRONG_PASSWORD" agent
```

Use real client email addresses only on the client's machine, and replace the example passwords before running the commands. Do not send passwords in the project archive or commit them to Git.

### 6. Start and check the backend

With the virtual environment active, run:

```powershell
python app.py
```

Keep this terminal open while the app is in use. On the first start, the local embedding model is downloaded and FAQ embeddings are created or refreshed. Wait until Flask reports that it is serving before opening the pages.

- Health and MongoDB check: `http://127.0.0.1:5000/health`
- Customer chatbot: `http://127.0.0.1:5000/`
- Calling-center dashboard: `http://127.0.0.1:5000/agent`
- Knowledge manager (admin login): `http://127.0.0.1:5000/knowledge`

The health endpoint should return `ok: true` and `mongodb: connected`. Sign in to the knowledge manager with the admin credentials and to the support dashboard with an agent/admin account.

### 7. Connect a Netlify frontend (optional)

The checked-in `index.html` currently has a temporary ngrok URL in `window.KORALINK_API_URL`. Before publishing the page for a client, replace it with the reachable HTTPS URL of the client's backend, for example:

```html
<script>
  window.KORALINK_API_URL = "https://api.client-domain.example";
</script>
```

Use the actual deployed backend URL; `api.client-domain.example` is only an example. Then publish the updated frontend to Netlify and set the backend's `FRONTEND_ORIGIN` to the exact Netlify site origin, such as `https://client-site.netlify.app`. If the client also opens the dashboard through the backend URL, the dashboard is already served by Flask at `/agent` and the knowledge manager at `/knowledge`.

For a temporary local demo, the frontend's API URL must point to the current ngrok HTTPS URL, and Flask's `FRONTEND_ORIGIN` must include the Netlify origin. The Flask process and ngrok tunnel must remain running. ngrok URLs are temporary and should not be used as the production backend address.

### Embed the chatbot on another website

After deploying the frontend files to Netlify, add this snippet to the client website where the chat button should appear. Replace both example URLs with the real addresses:

```html
<script
  src="https://YOUR-FRONTEND-SITE.netlify.app/static/widget.js"
  data-chat-url="https://YOUR-FRONTEND-SITE.netlify.app/"
  data-api-url="https://YOUR-BACKEND-SERVICE.example.com"
  defer
></script>
```

`data-chat-url` is the deployed `index.html` address, and `data-api-url` is the Flask backend address. The loader creates the floating button; clicking it opens the existing chatbot in a mobile-friendly panel. The same chat page continues to handle bot messages, human handoff, live-agent messages, and attachments. Do not use a temporary ngrok address for a permanent website integration.

The browser makes API and Socket.IO requests from the origin of `data-chat-url` (for example, the Netlify site), so that exact origin must be included in the backend's comma-separated `FRONTEND_ORIGIN` setting. Restart the Flask service after changing the setting. The website where the snippet is pasted does not need to host the Flask app; it only needs to allow the script and iframe to load from their configured URLs.

If both the chat page and backend are served by the same Flask domain, use that domain for all three URLs, for example `https://support.example.com/static/widget.js`, `https://support.example.com/`, and `https://support.example.com`.

## Local development

The steps above are the complete Windows first-time setup. On macOS/Linux, create and activate a virtual environment with `python3 -m venv venv` and `source venv/bin/activate`, then run `python -m pip install -r requirements.txt`; use the same `.env`, import, account, and startup steps. Keep `.env` private and use exact frontend origins rather than `*`.

### Embeddings and language handling

`EMBEDDING_PROVIDER=local` is the default. The first run downloads `sentence-transformers/all-MiniLM-L6-v2`; afterward embeddings run on the backend machine, so this part does not spend Hugging Face inference credits. Keep the model cache and enough RAM available on the host. To restore the previous hosted embedding provider, configure `EMBEDDING_PROVIDER=huggingface` and `HF_TOKEN`.

Automatic language translation uses external LLM APIs, not the local embedding model. It therefore still depends on provider quotas, current model availability, latency, and usage charges. The exact providers and model identifiers are configured in `groq_client.py`; check provider dashboards before a production launch.

## Knowledge import and recovery

The admin editor is the normal way to maintain live knowledge. `koralink_new.json` is the source for first import or intentional full replacement. `database.py` without replacement mode performs an upsert; use its `--replace-knowledge` option only when intentionally replacing the entire knowledge collection. Replacement creates a MongoDB JSON backup under `data/backups/` first. Review the script's help/output before running it and confirm that `.env` points to the intended database. Never use a full replacement to make a small individual edit.

Historical backup files are retained under `data/backups/`. Do not delete them until you have verified a separate copy and know the corresponding MongoDB content is no longer needed. The embedding cache is not a backup of knowledge records.

## Deployment workflow

### Testing with Netlify and ngrok

This is suitable for client demos only; your computer, Flask process, and ngrok tunnel must stay online. Configure the frontend API URL as the current HTTPS ngrok URL (no trailing slash). Set `FRONTEND_ORIGIN` to both the exact Netlify site origin and the ngrok origin used to open `/agent`, separated by a comma. Restart Flask after changing environment variables and redeploy the Netlify frontend after changing its API URL. Temporary ngrok hostnames can change, and the tunnel is not a stable production backend.

### Production outline

1. Keep the frontend on Netlify or another static host. Set `window.KORALINK_API_URL` in `index.html` to the stable HTTPS backend URL, or pass it as the `?api=` query parameter. Do not leave a temporary ngrok URL in the production build.
2. Deploy Flask as a persistent web service on a host that supports WebSockets/Socket.IO and has enough memory for the local embedding model. A small 2 GB service is a sensible starting estimate, but measure actual memory before selecting the final instance. The current `python app.py` entry point uses the development Werkzeug server; choose and configure a production server/runtime compatible with Flask-SocketIO before production launch, then verify concurrent live chats.
3. Configure a stable MongoDB Atlas cluster and network access restricted to the backend. Use a database user with only the access the app needs. Confirm storage and backup/retention requirements, especially for chat history and GridFS images.
4. Add secrets through the hosting provider's environment-variable manager, not source code. Set `SECRET_KEY`, MongoDB URL/database, language-model keys, `FRONTEND_ORIGIN` to the production frontend origin, `PORT`, and `EMBEDDING_PROVIDER=local`.
5. Deploy the backend and check startup/model download, health, logs, HTTPS, API calls, dashboard login, Socket.IO on a second device, agent replies, chat close, and attachment cleanup.
6. Deploy the frontend with the stable backend URL. Keep ngrok out of the production path.
7. Before accepting real customer data, add/review stronger authentication and session protections, rate limits, upload controls, operational monitoring, backup/restore procedures, privacy notice and retention policy. Arrange a client acceptance run and record a rollback/restore procedure.

The current app supports the core demo workflow, but the README does not represent a completed security audit or production certification. These deployment-hardening tasks should be included in the project delivery scope before launch with real customers.

## Useful API routes

Customer: `POST /api/customer/session`, `POST /api/customer/message`, `GET /api/customer/conversation/<id>`.

Agent: `POST /api/agent/login`, `GET /api/agent/queue`, `GET /api/agent/active`, `GET /api/agent/conversation/<id>`, plus claim, message, close, and attachment routes under `/api/agent/conversation/<id>/...`.

## Routine maintenance

- Edit knowledge in the admin page and keep a separate approved JSON export/version when making major content changes.
- Keep `.env`, `venv/`, `__pycache__/`, `data/question_embeddings.npy`, and `data/question_embeddings.npy.hash` out of client-facing source archives unless specifically needed. Never send `.env`.
- Keep Mongo backups in `data/backups/` or a secure off-device backup service. Restrict access because backups may contain customer or knowledge data.
- Remove only generated files that can be recreated. Do not delete `koralink_new.json`, the active embedding cache, Mongo backups, or environment files without first checking what depends on them.
- For code changes, review `git status` before sharing or deploying so secrets and customer data are not included.
